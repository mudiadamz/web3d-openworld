# Running it in the background on Windows

```powershell
# elevated PowerShell, from the project root
.\deploy\service.ps1 install     # installs, starts, and waits until it answers
.\deploy\service.ps1 status
.\deploy\service.ps1 restart
.\deploy\service.ps1 stop
.\deploy\service.ps1 logs
.\deploy\service.ps1 uninstall
```

Defaults to `http://127.0.0.1:8080`. `-Port`, `-Bind` and `-Name` override.
`npm run service:install`, `service:restart` and `service:status` are the same
thing from a package script.

Everything but `status` and `logs` needs an elevated shell.

## It is a scheduled task, not a services.msc service

Node cannot be a Windows service on its own. A service has to answer the Service
Control Manager's handshake within thirty seconds, and `node.exe` does not know
how: `sc create binPath="node.exe server.js"` installs happily and then fails to
start with **error 1053, "the service did not respond in a timely fashion"**.
Making a real one needs a wrapper binary.

A Scheduled Task does everything a service is actually wanted for here:

| | |
|---|---|
| starts at boot | `-AtStartup` trigger |
| runs with nobody logged in | runs as `SYSTEM` |
| restarts if it falls over | `RestartCount 3`, a minute apart |
| stop / start / restart | the verbs above |
| never killed for running too long | `ExecutionTimeLimit 0` — the default is three days |

**If you want a real services.msc entry**, put [NSSM](https://nssm.cc) on the
PATH and run `install` again. The script uses it automatically, every verb works
the same, and `status` tells you which backend you have. NSSM is also the better
stop: it sends a console event, so the server closes its database on the way
out. The NSSM path is written but untested here — there was no NSSM on this
machine to test it against.

## Stopping on Windows is not what it looks like

Worth knowing before you change any of this.

- **Windows has no SIGTERM.** `Stop-Process`, `taskkill` and `process.kill` from
  another process are all `TerminateProcess`. The handler in `server.js` never
  runs under any of them.
- **A console control event does reach it** — ctrl-C at a prompt, or what a
  service wrapper sends on stop. Node raises `SIGINT` for CTRL_C and `SIGBREAK`
  for CTRL_BREAK; `server.js` handles both, closes the listener, then closes the
  database.
- **`CTRL_C`, never `CTRL_BREAK`, from a script.** The event goes to every
  process on the console, which includes the script that sent it.
  `SetConsoleCtrlHandler(NULL, TRUE)` makes the caller deaf to CTRL_C **and only
  to CTRL_C** — CTRL_BREAK cannot be ignored. The first version of `stop` used
  CTRL_BREAK, stopped the server, and killed the PowerShell that was stopping
  it, half way through a restart.
- **It is best-effort, and that is fine.** A task may have no console to attach
  to, in which case nothing is delivered and `Stop-Process` finishes the job.
  The write-ahead log is crash-safe: an abrupt kill costs a recovery on the next
  start, not a world. The graceful close turns that from every restart into only
  the abrupt ones.

## Checks are made against the server, not against Windows

A task reports `Running` the moment it has launched something, and a service
reports `Running` once its wrapper is up. Neither knows whether a port got
bound — a task is `Running` with a process that exited on line one.

So every verb polls `GET /healthz`:

```json
{ "ok": true, "pid": 21392, "uptime": 3, "port": 8080,
  "chronicle": true, "node": "v22.14.0" }
```

`restart` additionally compares the pid before and against after. The same pid
means the stop quietly did nothing, which is the failure worth catching and the
one a "Running" status will never show you.

## Two things to know before exposing it

- **`DELETE /api/data` wipes every world, run and chronicle, and nothing asks
  who you are.** So do `DELETE /api/state` and `DELETE /api/worlds`. That is
  reasonable on `127.0.0.1`, which is why that is the default bind. `install`
  warns if you pass anything else. Put it behind something that authenticates
  before you open it up.
- **The chronicle needs Node 22+.** `node:sqlite` does not exist before it, and
  the server starts anyway with the chronicle off — the page runs, nothing is
  kept between worlds. `install` says so if it happens rather than leaving you
  to notice weeks later. `package.json` says `>=18` because that is true of the
  page; it is not true of the database.

## Files

| | |
|---|---|
| `deploy/service.ps1` | all of it. UTF-8 **with a BOM** — PowerShell 5.1 reads a BOM-less script as ANSI and mangles anything non-ASCII, so the body is ASCII too |
| `deploy/run.cmd` | generated by `install`; sets `PORT`/`HOST`/`NODE_ENV` and launches node. Machine-specific, gitignored |
| `logs/service.log` | stdout and stderr, appended. Gitignored |
